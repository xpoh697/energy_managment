## [2026-05-17 22:35] Задача: Исправление игнорирования пользовательских маппингов в translate_dp_mode из-за багов приведения типов в get_setting

### Archi
В версии `v11.9.556` был внедрен блок:
```python
if isinstance(val, str) and "." not in val:
    val = normalize_float(val)
```
Цель была благородной: нормализовать строковые целые числа (например, `"20"` -> `20.0`) для полей ввода. Однако разработчики забыли, что настройки режимов (например, `dp_map_sol` со значением `"sale_pv_no_bat"`, или `dp_map_solar` со значением `"sale_pv_no_bat"`) также являются строками без символа точки.
В итоге, любая текстовая настройка принудительно прогоняется через `normalize_float()`, падает с ошибкой `ValueError` и возвращает `0.0`. Это приводит к тому, что в `translate_dp_mode` срабатывает защитный fallback на `0.0` и принудительно выставляет `'sale_pv'` для режима `SOL`, полностью игнорируя пользовательскую настройку из Options Flow!

Предлагаю переписать логику на явную попытку конвертации:
```python
    if isinstance(val, str):
        try:
            float(val.replace(',', '.'))
            val = normalize_float(val)
        except ValueError:
            # Оставляем строку как есть, так как это строковая настройка (режим работы)
            pass
```

### Skeptic
Анализ решения Archi выявил 3 уязвимых места, критичных для производительности и надежности:
1. **CPU Overhead в симуляциях:** Метод `get_setting` дергается сотни раз в секунду внутри циклов `run_soc_simulation` и `get_dp_advice`. Механизм исключений (`try/except ValueError`) в Python очень дорогой. Постоянные попытки распарсить заведомо нечисловые строки режимов (вроде `"sale_pv_no_bat"`, `"stop_sale"`, `"buy"`) создадут серьезную паразитную нагрузку на CPU сервера Home Assistant.
   *Решение:* Использовать быстрое "символьное сито" перед `try/except`: строка может быть числом только если состоит из символов `0-9`, `.`, `,` и `-`.
2. **Лишние пробелы и Unicode:** В настройках могут проскакивать невидимые пробелы. Проверять нужно строго очищенную строку `val.strip()`.
3. **Безопасность числовых варнингов:** Мы должны гарантировать, что если в действительно числовое поле (например, емкость АКБ) передан поврежденный текстовый мусор, система выдаст лог-предупреждение `[ConfigError]` в конце метода `get_setting` через существующий блок `isinstance(default, float)`. Мой символьный фильтр идеально сохраняет это поведение, так как отсеет мусор и он попадет под логирование ошибок.

### Заключение
Консенсус достигнут:
- Перерабатываем блок парсинга строк в `get_setting` внутри `sensor.py`.
- Внедряем сверхбыстрый символьный фильтр для фильтрации нечисловых строк (режимов) без генерации дорогостоящих исключений CPU:
```python
    if isinstance(val, str):
        val_stripped = val.strip()
        # Быстрый фильтр на числовые символы для экономии CPU
        if val_stripped and set(val_stripped) <= set("0123456789.,-"):
            try:
                float(val_stripped.replace(',', '.'))
                val = normalize_float(val_stripped)
            except ValueError:
                pass
```
- Это вернет 100% работоспособность пользовательским маппингам и сохранит идеальную скорость работы симулятора.
